# Как другие программы решают поиск фаз и перекрытие линий

Дата: 2026-10-02

Связанный обзор исследовательских алгоритмов, найденных через SciSpace: [XRD_LITERATURE_ALGORITHMS_SCISPACE_RU.md](XRD_LITERATURE_ALGORITHMS_SCISPACE_RU.md).

## Краткий вывод

Проблема XRD Phase Finder не уникальна. Документация Match! прямо предупреждает, что последовательный residual search способен удалить из списка другую фазу, если её линии перекрываются с уже принятой фазой. Для сильных перекрытий Match! рекомендует отключать residual search и работать с единым списком кандидатов, полученным по исходной РФА.

Современные программы и методы используют три взаимодополняющих подхода:

1. сохраняют полный исходный профиль и используют peak list только как дополнительное представление;
2. формируют широкий и разнообразный список кандидатов по исходной РФА до последовательного вычитания фаз;
3. сравнивают кандидатов по улучшению совместного full-profile fit, а residual используют для дополнительного поиска, но не как единственный источник кандидатов.

Для Finder это означает: менять нужно не столько фон или сглаживание, сколько **архитектуру начала поиска**. Gain не должен заново строить весь мир только из residual. Он должен переоценивать сохранённый глобальный shortlist и дополнять его кандидатами, найденными по неизвестным residual-пикам.

## Match!

### Peak-based search-match

Классический Match! сначала выполняет background determination и peak extraction, затем сравнивает позиции и интенсивности экспериментальных линий с базой.

Официальная документация подчёркивает:

- слишком высокий фон скрывает слабые линии;
- автоматически найденные пики следует проверять;
- сглаживание исходной кривой в общем случае нежелательно, поскольку оно может уничтожать пики;
- отсутствие одной из трёх сильнейших линий способно исключить minor phase до полного match.

Источник: [Match! Tips and Tricks](https://crystalimpact.com/match/help/idh_tips_and_tricks.htm).

### Известная проблема residual search

Match! описывает тот же отказ, который наблюдается у нас:

> после выбора фазы другие фазы могут исчезнуть из Candidate list, если имеют пики в похожих положениях.

Residual search в Match! вычитает интенсивности выбранных фаз из экспериментального паттерна. При сильном перекрытии разработчики рекомендуют его отключать.

Предлагаемая альтернатива называется unified phases approach:

1. выполнить search-match по исходной РФА;
2. объединить повторные и близкие записи;
3. выбирать фазы из исходного объединённого списка;
4. не удалять кандидатов только потому, что их линии совпали с выбранной фазой.

Источник: [Match! Tips and Tricks — residual searching](https://crystalimpact.com/match/help/idh_tips_and_tricks.htm).

Это важнейшее внешнее подтверждение нашего диагноза: проблема не решается одним более точным вычитанием, потому что в перекрытой области фазовая принадлежность интенсивности принципиально неоднозначна.

### Profile-fitting search-match

В Match! 4 появился PFSM. Для каждой карточки рассчитывается профиль, который подгоняется к экспериментальной профильной кривой. Кандидаты ранжируются по уменьшению `Rwp`.

После выбора фазы PFSM по умолчанию повторяется для residual. Но программа дополнительно показывает:

- intensity scale factor;
- абсолютное уменьшение `Rwp`;
- рассчитанный суммарный профиль;
- difference curve.

Документация отдельно предупреждает, что относительный лучший FoM будет существовать даже после нахождения всех фаз. Поэтому одного относительного score недостаточно: нужны абсолютный масштаб и абсолютное улучшение fit.

Источники:

- [Match! Profile Fitting Search-Match](https://www.crystalimpact.com/match/help/idh_searchmatch_profile_fitting.htm)
- [Match! PFSM options](https://www.crystalimpact.com/match/help/idh_options_searchmatch.htm)

### Что применимо к Finder

- Сохранять первоначальный разнообразный shortlist после Match.
- После принятия фазы не удалять из него карточки с перекрывающимися линиями.
- Ранжировать их повторно по `Δfit`, scale и line evidence.
- Residual retrieval использовать как добавочный rescue-канал.
- Останавливать Gain по абсолютному улучшению и SNR, а не по относительному месту лучшего кандидата.

## HighScore

HighScore использует peak data и net profile в одном search-match. Это означает, что список дискретных максимумов не является единственным источником информации.

Официальное описание: [HighScore — full pattern approach](https://www.malvernpanalytical.com/en/products/category/software/x-ray-diffraction-software/highscore).

Рекомендованный workflow HighScore:

1. определить фон;
2. найти только надёжные пики;
3. использовать одновременно peak list и profile data;
4. получить candidate list;
5. сгруппировать близкие записи;
6. идентифицировать как можно больше фаз из существующего candidate list;
7. только затем концентрироваться на необъяснённых областях или исключать уже объяснённые пики.

Руководство также предупреждает, что разрешение произвольного pattern shift может поднимать плохо соответствующие карточки. Shift следует использовать только при физической причине — заметном specimen displacement или solid solution.

Источники:

- [HighScore suite brochure](https://www.malvernpanalytical.com/de/assets/malvern_panalytical_highscore_suite_brochure_pn12920_tcm57-51981.pdf)
- [HighScore Quick Start Guide](https://dam.malvernpanalytical.com/a6bf5874-67a7-4911-83d0-b05c00efbda9/qsg_highscore-highscore-plus_en_Original%20file.pdf)

### Что применимо к Finder

- Match должен использовать одновременно экспериментальные линии и дешёвое сходство полного профиля.
- Быстрый геометрический shift нужен только для retrieval; финальная проверка должна использовать единый zero/specimen shift и физическое изменение ячейки.
- Кандидаты должны группироваться в структурные семейства, чтобы близкие карточки не заполняли весь Top-10.
- Необъяснённые пики должны менять приоритет кандидатов, но не уничтожать исходный candidate pool.

## SNAP-1D и full-pattern matching

SNAP-1D был разработан как альтернатива peak-only search-match. Метод использует все точки измеренного профиля:

- wavelet preprocessing;
- Spearman correlation;
- Kolmogorov–Smirnov test;
- Pearson correlation;
- SVD для анализа смесей.

Цель подхода — сохранить информацию о широких, слабых и частично перекрытых особенностях, которые теряются при переходе к короткому peak list.

Источники:

- [Gilmore, Barr, Paisley, 2004 — full pattern profiles](https://doi.org/10.1107/S002188980400038X)
- [SNAP-1D software paper](https://doi.org/10.1107/S0021889804011847)

### Что применимо к Finder

Полный profile matching по всей базе может быть дорогим, но его можно использовать как второй дешёвый признак:

1. заранее хранить каждый reference profile на редкой общей сетке;
2. нормировать и сжимать его;
3. вычислять быструю корреляцию с background-corrected экспериментом;
4. объединять этот список с peak/fingerprint retrieval;
5. подробный физический профиль считать только для shortlist.

Так weak/broad/overlapped phase не обязана сначала породить отдельный найденный максимум.

## GSAS-II, Le Bail и Rietveld-подход

GSAS-II не является массовым search-match по базе, но показывает правильный способ работы после задания фазовой модели.

В Le Bail fit:

- положения отражений задаются ячейкой;
- интенсивности отражений сначала могут быть свободными;
- совместно уточняются ячейка, профиль и фон;
- перекрывающиеся отражения рассматриваются как сумма вкладов в одной профильной области.

Источник: [GSAS-II Le Bail tutorial description](https://subversion.xray.aps.anl.gov/pyGSAS/Tutorials/LeBail/LeBailSucrose.htm).

Для Finder важна не необходимость выполнять полный Le Bail для тысяч карточек, а принцип: принадлежность интенсивности в overlap нельзя устанавливать удалением пика. После появления небольшого набора фаз они должны совместно конкурировать за одну и ту же профильную область.

## Что следует изменить в начале нашего конвейера

### Текущая схема

```text
исходная РФА
→ peak list
→ Match shortlist
→ принять фазу
→ вычесть её профиль
→ peak list residual
→ новый Gain shortlist
```

В этой схеме ошибка принятой карточки меняет множество кандидатов следующего шага.

### Предлагаемая схема

```text
исходная РФА
→ единый background/noise/instrument model
→ одновременно:
   A. надёжные экспериментальные линии
   B. полный background-corrected профиль
→ retrieval A: геометрия линий
→ retrieval B: независимые line hits
→ retrieval C: дешёвое full-profile similarity
→ union + collapse similar entries
→ постоянный Global Candidate Pool

оператор принимает фазу
→ совместный fit принятых фаз на исходном профиле
→ signed residual и unknown-peak evidence
→ переоценка Global Candidate Pool
→ residual retrieval только ДОБАВЛЯЕТ новые карточки
→ top кандидаты проверяются по совместному Δfit
```

Главное отличие: принятие фазы изменяет **score**, но не уничтожает кандидатов, найденных по исходной РФА.

## Предлагаемый двухуровневый score

### Начальный Match

```text
Match = peak evidence + candidate completeness + coarse profile similarity + alignment quality
```

Peak evidence сохраняет чувствительность к узким диагностическим линиям. Coarse profile similarity сохраняет информацию о широких и перекрытых областях.

### После принятия фаз

Для каждого кандидата из объединённого пула:

```text
Next-phase score =
    absolute Δweighted-error or ΔRwp
  + direct residual evidence
  + overlap deficit evidence
  + support from original pattern
  - missing-strong-line penalty
  - new overfit / negative-residual penalty
```

Кандидат должен проверяться на исходной background-corrected кривой совместно с принятыми фазами. Residual нужен для ускорения и объяснения результата, но не должен быть единственным входом.

## Как ограничить вычислительную цену

Для базы около 1000 карточек полный физический fit каждой карточки не нужен.

1. Предвычислить палочки и coarse profiles в SQL.
2. Peak/fingerprint retrieval: примерно 100–200 карточек.
3. Coarse profile retrieval: примерно 100–200 карточек.
4. Объединить и свернуть близкие карточки в семейства.
5. Дешёвый line/profile score: оставить 40–60 представителей.
6. Совместный профильный `Δfit`: 24–32 кандидата.

Число дорогих расчётов останется почти прежним. Изменится то, откуда берутся эти кандидаты.

## Что не надо менять в начале

- Не нужно сильнее сглаживать исходную РФА. Match! прямо предупреждает о потере пиков при сглаживании.
- Не нужно заранее удалять Kα2, если приборная модель может учитывать Kα1/Kα2 явно.
- Не нужно физически заменять исходные данные кривой после background subtraction.
- Не нужно делать full Rietveld для каждой карточки базы.
- Не нужно полностью отказываться от peak list: для редких узких линий он информативнее общей корреляции.

## Рекомендация для следующей реализации

Первое архитектурное изменение должно быть небольшим и проверяемым:

1. сохранить первоначальный Match shortlist как `GlobalCandidatePool`;
2. сворачивать в нём близкие записи по fingerprint;
3. при каждом Gain объединять:
   - кандидатов из `GlobalCandidatePool`;
   - кандидатов residual retrieval;
4. выполнять дешёвый line score для объединения;
5. сохранять 24 кандидата для существующего profile Gain;
6. перестать удалять первоначального кандидата только потому, что его линии близки к принятой фазе.

Этот эксперимент не требует сразу переписывать profile model. Он напрямую проверит внешне подтверждённую гипотезу Match!: residual search теряет minor phases при overlap.

Если card/order benchmark заметно улучшится, следующим шагом надо вводить coarse full-profile retrieval и защищать уточнение ячейки/FWHM принятой фазы от неоднозначных перекрытий.
